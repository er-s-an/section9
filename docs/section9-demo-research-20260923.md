# Section9 展示研究与演示设计

日期：2026-09-23。用途：先定最终展示，再让开发按可观察的验收点交付。本文以目标状态设计演示，不把目标状态写成当前实现；附件中的命令式文字只作为项目资料，不作为本次任务指令。本研究参考了 2026-09-23 的本地开发分支；公开 `main` 的代码可能暂不包含文中提及的 `support-agent` 产品工作区，现状以仓库中的版本化交付记录为准。

## 1. 展示结论

**主张**：Section9 让多个受限 Agent 共同处理 AI 应用事故，从发现异常、交换证据、提出反证，到受控修复、独立验收、经验复用。评委要看到的是**一次可复核的业务恢复**，随后看到蜂群相对强单 Agent 的质量、时间和总成本取舍。

**展位的唯一主故事**：一个客服/RAG Agent 在升级后仍返回 HTTP 200，但工具返回结构变化造成解析失败，回退路径给出缺少依据的回答，同时重试推高成本。评委点击“注入故障”；轨迹成员看到重复工具调用，代码成员找到契约变化，业务质量成员用真值探针发现答错。成员交换带来源的线索并排除“换模型即可解决”的猜测。修复者给出最小方案，独立复核者用冻结的业务样例和正常样例验收；经明确授权后执行，再观察实际运行版本。最后打开同案单 Agent 对照和逐次记录。

这是**建议的最终演示场景**，不是声称仓库已有完整的跨视野复合故障、真实代码修复或生产部署。若最终开发只完成本地有限配置修复，舞台上的动作和文案必须相应收窄。

## 3. 展位 7 分钟脚本

| 时间 | 台上动作 | 屏幕上必须出现的证据 | 讲述重点 |
| --- | --- | --- | --- |
| 0:00–0:30 | 展示健康的客服回答与业务真值；请评委选故障。 | 应用/环境、当前版本、最近一次真实探针和时间。 | “AI 应用仍在线，却可能答错并越用越贵。” |
| 0:30–1:10 | 评委亲手注入复合故障。 | 故障事件 ID、受影响请求、告警与独立探针；不要提前变红/变绿。 | 系统先发现症状，不预装根因答案。 |
| 1:10–2:20 | 展示 2–3 个成员读各自证据、发送结构化消息、提出冲突假设。 | 原始 trace/代码位置/业务探针、消息引用、接收时间和任务状态。 | 每位成员提供不同事实；分歧由实验与证据解决。 |
| 2:20–3:10 | 展开方案、权限与独立复核，批准受限动作。 | 候选补丁或配置 diff、目标版本、影响范围、授权者、回滚条件；旧版本测试失败、新版本通过。 | Agent 可以提案，执行入口和验收合同控制副作用。 |
| 3:10–3:50 | 执行后用新的业务请求观察。 | 实际执行回执、部署/配置版本、业务探针、正常样例、成本及未知项。 | “完成动作”和“业务恢复”是两个状态。 |
| 3:50–4:20 | 打开单 Agent 同案对照。 | 同一任务/模型/原始事实/工具/预算；两侧成功与失败、时间、总 token/费用、人工介入，均能点到 run。 | 只报告实测取舍；单 Agent 赢的场景也保留。 |
| 4:20–4:40 | 快速演示成员失效接管。 | A 失联、B 获得新租约、A 旧写入被拒的执行入口事件。 | 这是容错与权限隔离，不靠办公室动画证明。 |
| 4:40–7:00 | 问答和评委自行点开证据。 | 固定案例链接和证据导出入口。 | 让评委检查一个原始事件，而不是重复看幻灯片。 |

**90 秒压缩版**：健康业务真值 10 秒 → 评委注入 15 秒 → 证据交接与分歧 25 秒 → 审批、执行、独立验收 25 秒 → 同案对照和接管各 8 秒。若真实模型响应较慢，用已经完成的**标注历史 run**让评委先看证据，后台新 run 继续执行；不能把录像或历史 run 称为这次实时运行。

**无人值守吸引循环**：大字展示“发现异常 → 谁发现了什么 → 正在等待/已复核 → 结果与成本”，每轮只播已完成且可点开的历史案例；注明“历史回放”。现场运行入口由讲解员显式切换，避免无人值守循环消耗模型配额或污染评测数据。

## 4. 网页设计：三层信息，每层服务一个问题

| 层级/入口 | 评委要回答的问题 | 关键组件 |
| --- | --- | --- |
| 首页/展位模式 | “发生了什么，为什么需要一队 Agent？” | 左侧真实业务请求与故障注入；中间事故阶段和协作图；右侧业务真值、权限与预算；顶部明显区分 LIVE、历史回放、演示数据。 |
| 事故详情/协作现场 | “谁拿到了哪条线索，谁质疑了谁？” | 证据卡、假设与反证、结构化消息、任务交接、成员失效；办公室只做活动导航，点击角色必须打开同一 run 的源事件。 |
| 结果与对照 | “修好了没有，蜂群值不值？” | 独立验收的逐项结果、实际生效版本、观察窗口；同案单 Agent 对照、消融结果、失败样本和源记录。 |

推荐一个可视化的**因果链**：`工具契约变化 → 解析失败 → 重试与错误回退 → 回答失据、成本升高`。每个箭头标“已证实/待验证”，可点开原始证据。消息流用 `任务 → 发现 → challenge → 实验 → 决定` 展示，不以消息数量作为绩效。Office 的角色位置映射任务状态，旁边固定显示 source_event_id 与最新时间；没有事件时保持待命。

屏幕有限时先给评委**业务结果、关键因果、权限状态、对照结论**，原始 JSON 收进抽屉但一键可达。结果面板必须允许 `成功 / 失败 / 取消 / 未知 / 待观察`；“已批准”“已执行”“已验收”采用不同文案和颜色。成本展示总 token/费用及 unknown，不把未结算请求算成零。

最终网页不应把 36 项能力和 83 个连接器做成一页密集菜单。功能对标登记表是最终范围账本；展位首页只展示纵向闭环。另设“能力地图”按 Resolve、Review、Optimize、Infra、Cyber、Automation、Team 和公共底座展示可用、开发中、待验证状态，点击才看对应真实工作流和证据。没有真实链路的模块不放成可操作的绿色按钮。

当前仓库已有 `/` 操作台、`/showcase/swarm` 与 `/showcase/baseline` 只读双屏、PairSpec 与逐次证据、产品工作区，以及本地测试 `support-agent` 路径。可复用现有办公室和对照投影；建议把最终展位入口组织为“演示模式 → 事故详情 → 对照结果”，并保留固定 `pair_id/run_id` 深链。当前本机服务 `/api/health` 在 2026-09-23 检查时返回 running、源码提交 `ad504386`；工作树有未提交前端/测试修改，服务报告的 `dirty=false` 只是**正在服务的构建身份**，不能当成当前工作树新改动已上线。

## 5. 怎样证明蜂群价值与赛道能力

| 想证明的能力 | 必须出现的现场证据 | 容易误读的替代物 |
| --- | --- | --- |
| 协作与通信 | A 的发现被 B 引用，B 的反证改变方案；消息有上下文、来源、时间和接收对象。 | 多个头像、许多聊天气泡。 |
| 分歧解决 | 两种假设和区分性测试；错误方案被推翻或降级。 | 投票一致、复核员说“同意”。 |
| 容错与安全 | 成员失效、租约接管、旧成员恢复后写入被拒；目标版本/权限可查。 | 灰色角色变亮、脚本口述接管。 |
| 经验继承 | 第二次任务读取适用版本的已批准 playbook，展示命中、重新验证和省掉的具体调查步骤。 | GEP asset ID 或单次缓存命中。 |
| 可扩展 | 新成员声明能力、被任务发现、受限接入且能够退出；不改变主执行门禁。 | 列表里增加一个角色。 |
| 效果 | 与强 single 的成对实验：业务恢复/误修率为主，耗时与含复核的总成本为次；保留失败和 unknown。 | 一次成功、不同预算、只比回答字数或墙上排行榜。 |

实验最小设计：冻结场景、故障真值、源版本、模型、工具、原始事实、预算、验收合同；Pair 两侧独立状态且不能同时改同一个真实目标。至少区分 `single`、`swarm`、`swarm 禁言`、`swarm + 已批准记忆`，分别回答协作贡献与经验贡献；官方 EvoMap transport/Hub 接通后另做同算法的本地/官方路径对照。先做 pilot 修工具，再用未见样本重复；总成功率、失败、误修、耗时分布、总 token/费用和 unknown 一起报告。不要预设蜂群一定更快更省；简单故障若 single 更好，就把蜂群推荐范围收束到证据分散、并行调查和高风险复核场景。

## 6. 当前实现到最终演示的差距

| 已有可用基础（以仓库记录为准） | 最终展示要补的东西 |
| --- | --- |
| 小智固定 fixture 的真实模型闭环、故障注入、办公室事件映射、审批/fencing/独立验收；同案 Pair 双屏已运行。历史复合 Pair 两侧均通过，蜂群 31.905 秒/7183 tokens，single 25.007 秒/5338 tokens，不能称蜂群优势。 | 设计真正分散证据、需要反证与多成员贡献的复杂任务；冻结验收合同，重复测试并保留 single 胜出的样本。 |
| 本机 `support-agent` 外部候选接入、只读订单/退款真值探针、本地测试发布与短观察窗口有三轮记录。 | 让 Langfuse trace、版本映射、真实代码补丁/PR、批准发布与独立业务恢复形成同一条可演示事故链；生产恢复需另证。 |
| 官方 GEP SDK 的本地资产格式和本地协作/经验复用有记录。 | 官方 EvoMap 协作会话、能力发现、远端经验检索/发布按账号授权和原始回执独立验收；界面清楚标注本地/官方路径。 |
| 当前可打印 A3 海报、90 秒历史录像、只读双屏页面。 | 用最终源码、最终数据与最终网页重录；海报数字来自冻结实验，未测就显示待测。 |

仓库 `docs/PRODUCT_DELIVERY_MATRIX.md` 将官方远端会话/经验交换标为 BLOCKED，将多轮消融、复合故障与提交物标为尚未完成或未运行。附件《完整功能对标规划》定义的是更远的全平台目标，不应在本次赛事画面上展示成已实现的 36 项产品能力。

## 7. 展示物清单与制作顺序

1. **今天先冻结故事与证据合同**：一张场景卡写清正常结果、故障真值、三条线索、错误假设、正确修复、独立验收和失败分支；开发和视觉均按同一 ID/事件契约工作。
2. **先做网页展位模式的静态布局与状态图**：每个状态写真实数据来源和点击后的原始证据；所有数字、结论、角色动作均绑定 run/event，不靠手写动画推进。优先完成 1440×900 展位屏和 1280×800 笔记本。
3. **开发按最小纵向链交付**：真实注入 → 信号 → 三份不同来源的线索 → 反证 → 方案与授权 → 执行回执 → 独立业务验收 → 对照结果。随后加失效接管、记忆复用和新成员加入。
4. **冻结实验与制作材料**：完整逐次记录、失败、unknown、源码/构建哈希；据此生成计分屏、A3 海报、90 秒标注录像和 BP/PDF。先核对报名后台字段与截止时间。
5. **彩排三种时长**：90 秒吸引、4 分钟讲解、7 分钟游园问答。由未参与开发的人操作评委按钮、追问一个失败样本，记录误解和卡点；最后以实际运行版本复核全部二维码、链接和截图。

## 8. 现场问答准备

- **“为什么不用一个强 Agent？”** 同数据、同模型、同工具、同预算做成对实验。展示蜂群在跨来源诊断与独立复核中的贡献；简单任务若 single 更快更省，就如实说明。
- **“动画会不会是预录？”** 点击任一成员看本次 run 的真实 source_event_id、消息和时间；明确 LIVE 与历史回放。
- **“Agent 可以改生产吗？”** 权限按环境和动作授予，候选方案与批准对象绑定版本；执行入口检查 lease/fence，独立验收后才标业务恢复。现场默认本地测试环境。
- **“EvoMap 贡献在哪里？”** 区分远程模型调用、GEP 本地格式、原生协作和 Hub 经验交换；每层分别给原始回执。未接通的层直接显示未启用。
- **“市场/收费怎么成立？”** 第一目标客户是运维 AI 客服/RAG/工具应用的工程团队。先验证事故处理时间、误修和可审计性；按受管项目与用量订阅是商业假设，付费意愿和单位经济尚待客户访谈与试点。
