# Product API v1 contract freeze

Status: **v1 domain semantics are defined; durable workflow implementation is partial**. This document covers the M1/M2 product contract boundary from planning §§6–7 and 18. The Pydantic source of truth is [`s9/product/v1_contracts.py`](../../s9/product/v1_contracts.py); contract and workflow regressions are in [`tests/product/`](../../tests/product/).

## Scope and compatibility

- New product resources use `/api/v1`. Existing `/api` and `/agent` remain legacy laboratory/worker interfaces until an explicit migration is implemented.
- Resource IDs are opaque server-generated identifiers. The storage layer checks workspace, application, environment, connection, and binding relationships. The current local setup routes do not yet resolve an authenticated multi-user principal; local-origin controls are a single-machine operator boundary, not production identity or authorization.
- `workspace_id` is the product data and authority boundary. Current `ProductRegistry(project_id, environment_id)` and lab `Pair` identities are not silently renamed or migrated into this boundary.
- Commands carry an `Idempotency-Key` and an object revision (`If-Match` or equivalent `expected_revision`). A same-key/same-content retry returns the same receipt; same key with different content conflicts. Stale revisions conflict. Authorization is rechecked at the final side-effect dispatch point.
- Long operations return an accepted job/run identity and a status URL. HTTP acceptance does not mean investigation success, approval, execution, or business recovery.

## Domain resources

| Resource | Contract responsibility |
| --- | --- |
| Workspace | Policy, budget, deployment mode, and outer data boundary. Validation reserve cannot exceed the token limit. |
| Application | Governed application identity and owner within one workspace. It is not an Agent process. |
| Connection | Provider endpoint, non-secret credential reference, capabilities, and separate connection health. Secret values are never API fields. |
| ScopeBinding | Explicit application/environment/resource binding and granted read/write scopes, independently versioned. |
| Signal | Source identity, source time and observed time, dedupe key, and coverage-relevant intake record. |
| Incident | Long-lived business issue with signals, severity, state, and outcome. A failed attempt does not delete or terminate the incident. |
| InvestigationRun | One bounded, versioned investigation with frozen input snapshot and budget. A terminal run is never reactivated; a retry creates a new run. |
| Task | Bounded capability/dependency assignment with a lease epoch and holder; server validates capabilities and dependencies. |
| Hypothesis | Revisable explanation with explicit supporting and counterevidence references; never an authority credential. |
| Evidence | Immutable source/version/time/hash/classification reference with separate raw and sanitized artifact references and coverage state. |
| ProposalVersion | Immutable, content-hashed target/action/risk/rollback/validation/budget snapshot. Approval applies to that exact version and its scopes. |
| ExecutionAttempt | One idempotent, fenced attempt against captured resource versions. `outcome_unknown` requires reconciliation; it does not trigger a blind retry. |
| ValidationReport | Independent checks bound to the actual applied version, validation contract hash, and evidence references. |

ReviewFinding, OptimizationFinding, and SecurityFinding remain domain-specific work-item types. Shared authority, execution, evidence, budget, event, and audit services do not erase their business fields.

## State and result semantics

- Incident state and InvestigationRun state are independent. An Incident may remain open while one run is failed, cancelled, inconclusive, or interrupted.
- `InvestigationRun.succeeded` means the investigation deliverable completed. It does not mean the service recovered.
- Proposal content changes create a new `ProposalVersion`; they invalidate prior approval. Approval does not hold a task lease while waiting for a person.
- Execution progresses through queued, authorized, dispatch committed, and running to applied, not applied, or unknown. Applied execution still requires independent validation and any configured observation window.
- `accepted_risk` and `archived_unresolved` are not synonyms for resolved.
- Source events, model hypotheses, operator decisions, execution outcomes, and validation checks retain distinct provenance and event types.

## Error and asynchronous response envelope

Errors use `{ "error": { "code", "message", "retryable", "scope_ref", "request_id", "details", "next_action" } }`. Client retry behavior uses `code` and `retryable`, not message parsing. Intended HTTP classes are: 401/403 identity or permission, 409 revision/idempotency/state conflict, 422 invalid business input, 429 budget/rate limit, and 503 unavailable dependency. An uncertain external side effect is an explicit `outcome_unknown` result, not a retryable generic 503.

Long-running commands return an `AcceptedJob` with `job_id`, queued/running state, `status_url`, `request_id`, and acceptance time. Result status is read separately.

## Concurrency and evidence rules

- Every read and write is checked against the resolved workspace/application/environment relationship.
- Write operations are idempotent within their scope and target exact revisions. Competing decisions return conflict; later arrival does not overwrite the earlier authority result.
- State, budget reservation/settlement, and outbox event are committed together in the local database where possible. External APIs are not covered by a claim of exactly-once delivery; record dispatch intent and reconcile uncertain results.
- Evidence export identifies its source watermark, schema version, coverage gaps, redaction policy, file count, and file hashes. Hitting a page or size limit is visible and never named a complete export.
- Secret values, provider keys, and raw restricted artifacts do not appear in ordinary object schemas or agent-visible records. A credential reference is an opaque pointer, not a secret.

## Implementation boundary

The contract models are strict (`extra=forbid`) and immutable at model assignment. Implemented setup resources are Workspace, Application, Connection, and ScopeBinding: additive SQLite migrations, scoped foreign keys/lookups, local `/api/v1` create/list/get routes, idempotency receipts, a workspace event log, and local UI. The migration is applied when a ProductRegistry is initialized; it has been exercised against temporary databases, not the currently running user database. Signal/Incident now have a first durable slice: source-versioned, scope-bound deduplicated Signal intake; bounded Langfuse/GitHub imports with persisted per-window cursor/coverage checkpoints; Signal listing; revision-checked Incident creation; revision-checked operator attachment of new Signals to an active Incident; and atomic signal-linking, status changes, and audit events. Operator attachment requires a reason and current Signal/Incident revisions. A limited repeat-source rule also appends a polled new version of the exact same object only when a prior version was linked within 24 hours to exactly one active Incident in that same binding. Ambiguous or older repeats stay in the inbox. This identity-based rule does not infer causality from timing, similar services, or different sources.

Read-only validation currently has Langfuse one-row bounded observation checks and GitHub repository metadata/default-branch/root-list checks. They use explicit `S9_OBSERVED_` environment references and fixed/validated endpoints. Their API and browser tests use provider mocks; real account access has not been verified.

Opt-in scheduled Signal polling now uses the same bounded import handlers as manual reads. `GET /api/v1/workspaces/{workspace_id}/applications/{application_id}/signal-monitors?environment_id=...` lists monitor policy and health; `PUT /api/v1/workspaces/{workspace_id}/applications/{application_id}/scope-bindings/{binding_id}/signal-monitor` creates, resumes, or pauses one monitor with `enabled`, `interval_seconds`, and `expected_revision`; `GET /api/v1/workspaces/{workspace_id}/applications/{application_id}/signal-monitors/{monitor_id}/runs` returns its run history. Enabling requires a verified Langfuse project or GitHub repository scope and an explicit local operator action. Polling is read-only, starts at the enable time, runs at a 60-second to 24-hour interval, and reads at most five pages of 100 records per run. Cursors and windows survive restarts; 429/5xx failures back off, while missing credentials, permission loss, or scope conflicts pause the monitor. After more than 24 hours offline, the worker records the skipped interval and resumes over the newest day instead of silently replaying an unbounded backlog. The operator UI refreshes monitor status every 15 seconds while a monitor is enabled; that refresh only reads the local API and does not contact a source. These guarantees are local code/test evidence only; provider credentials, real account behavior, and multi-user authorization remain unverified.

Signal and Incident lifecycle/state transitions remain partial. Revision-checked merge and split operations move signal relationships in one SQLite transaction, retain the merged source Incident with an explicit target, and record reasons and moved IDs in workspace events. Both operations reject terminal incidents, stale revisions, and active investigation runs; split must leave at least one signal on the source. The local single-operator surface can claim/release an Incident as `local-operator` and adjust active Incident severity; these writes require the current revision, an operator reason, idempotency, and an audit event. This is not a team identity or RBAC claim. Merge, split, assignment, and severity operations are available under `/api/v1/workspaces/{workspace_id}/applications/{application_id}/incidents/{incident_id}`. Manual InvestigationRun, Evidence references derived from frozen Signals, versioned Hypotheses, operator decisions, and manual run completion are durable. `execution_mode=manual` makes that boundary explicit. These operator-entered outcomes are not independent verification or automated RCA.

`POST /api/v1/workspaces/{workspace_id}/applications/{application_id}/incidents/{incident_id}/investigation-runs` creates a `single` or Section9-owned `swarm` run and its initial task graph in the same SQLite transaction as the frozen input and Evidence. The initial graph is deterministic: `single` uses one investigator with all frozen Evidence; `swarm` fans investigators out by source binding, then creates a challenger seed with no task dependencies, a review depending on the seed and every investigator, and a synthesizer depending on the review and investigators. The loopback-only operator routes under `/workspaces/{workspace_id}/applications/{application_id}/workers` register, list, rotate, and revoke environment-scoped Worker bearer credentials. A token is returned once and only its SHA-256 digest is stored. `/investigation-runs/{run_id}/tasks/{task_id}/claim`, `/context`, `/renew`, and `/finish` require that token; the server resolves Worker identity and capabilities from the registration, while a request may only narrow the granted capability list. `/retry` remains an explicit local-operator action. The protocol retains bounded leases, structured outputs, same-run evidence validation, and epoch fencing. The task context endpoint only projects a worker's assigned Evidence and completed dependency results; the seed therefore cannot receive investigator outputs through that endpoint. Task findings create `proposed` Hypotheses with task and epoch provenance. A completed graph leaves the run active for operator judgment and does not mean a confirmed root cause or recovered service.

`PUT /api/v1/workspaces/{workspace_id}/budget` revisions the Workspace budget and policy atomically. Investigation runs capture `policy_revision`; a change makes remaining model dispatches fail closed. `POST /api/v1/workspaces/{workspace_id}/applications/{application_id}/investigation-runs/{run_id}/execute` runs the existing graph through serial, isolated chat-completions requests. Each task must return a role-valid `TaskResult`; evidence references are checked before persistence. The operator UI requires a positive token limit and a separate execute action. Migration v7 adds an investigation usage ledger with reservation, dispatch-committed, settled, and outcome-unknown states; migration v8 adds authenticated environment-scoped Worker registrations. UTF-8 request bytes plus the output cap are reserved before dispatch; reported provider usage settles the reservation, while any post-dispatch response without reliable usage retains the full reservation. After a process restart, execution checks expired task leases: a task with no dispatched model request is reopened; a request left dispatch-committed becomes outcome-unknown and retains its full reservation; a known settled request whose TaskResult was not stored is failed with its known usage. The runtime never automatically resends an uncertain request. An operator may explicitly retry a failed task, which can issue another paid request. Run detail shows the task graph and usage records.

The local task runtime is covered by temporary-database tests with `httpx.MockTransport` and a Playwright flow with API stubs. No real provider request was made. The same configured model serves each role serially; this is not multi-model or parallel execution, has no tool loop, and does not verify statistical independence. Worker bearer and recovery tests use local API/database state; process interruption is represented by persisted lease/usage states, not a killed process during a real provider call. This local Worker registration is not team identity, RBAC, or a remote control-plane boundary. The deterministic planner is not an EvoMap task service. The context projection is not a security boundary against a caller that also has the local operator API. Automatic grouping/cooldown/routing, dynamic task planning, authenticated team identity, independent review, proposal lifecycle, human approval, controlled remediation, reconciliation, independent recovery validation, EvoMap native collaboration, and release/deployment acceptance remain implementation work. No route returns a synthetic success to imply those capabilities exist.
