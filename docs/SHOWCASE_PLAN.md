# Section9 最终展示规划

日期：2026-09-23。本文定义目标演示和开发验收口径，不是已完成能力清单。公开 `main` 的实现与证据见[交付记录](DELIVERY.md)、[双屏交付记录](SHOWCASE_DELIVERY.md)和[当前可复跑演示](DEMO.md)。[完整功能对标规划](planning/Section9_完整功能对标与蜂群架构实施规划.md)、[JSON 登记表](planning/Section9_功能对标登记表.json)与[展示研究](section9-demo-research-20260923.md)均为规划资料。

## 一句话与观众任务

Section9 给维护 AI 应用的团队一支受控运维蜂群：成员用不同来源的证据协作调查、反证和修复；权限系统决定能否执行；独立业务验收决定能否结案。评委应能亲手触发问题、观察一次真实处理，并检查每个关键结论的来源。

## 一件主故事

目标案例：客服/RAG Agent 升级后，检索工具返回结构变化。应用仍响应 HTTP 200，但解析失败触发错误回退，回答失去依据；工具重试增加成本。轨迹成员发现重复调用，代码成员定位契约变化，业务质量成员用真值探针发现答错。三份线索汇合后，小队排除“只换模型”的不充分方案，提出最小修复；独立成员检查旧版失败、候选版通过和正常场景无退化。经明确批准后执行，系统再检查实际生效版本及业务探针。

这个案例是开发目标。公开 `main` 有小智固定 fixture 与历史 Pair；后续本地开发分支另有 `support-agent` 测试候选。不能把它们拼接成一次已经完成的外部应用事故。若开发结果只覆盖有限配置动作，现场必须按实际动作讲述。

## 展位网页

| 页面 | 第一眼要回答的问题 | 必须能追溯的内容 |
| --- | --- | --- |
| 演示首页 | 什么业务坏了，现在谁在处理？ | 应用与环境、真实业务请求、故障注入事件、最新探针、预算与运行/回放标记。 |
| 事故与协作 | 谁提供了什么证据，分歧怎样解决？ | trace/代码/业务证据、假设和反证、结构化消息、成员失联与接管、每个动作的事件 ID。 |
| 方案与验收 | 改了什么，谁允许，业务真的恢复了吗？ | diff 或配置变更、目标版本、审批范围、执行回执、独立检查与观察窗口。 |
| 对照实验 | 蜂群相对强单 Agent 的取舍是什么？ | 同案规格、两侧全部运行、成功/失败、误修、耗时、总 token/费用、unknown 和导出。 |

办公室提供协作导航。角色活动来自任务事件；点击角色可打开同一个 run 的原始记录。动画、消息数量和 GEP asset ID 均不能代替业务效果。状态应区分 `LIVE`、带日期与源码身份的历史回放、演示数据；还应区分已批准、已执行、待观察、已恢复、失败和未知。

最终全平台范围以另行维护的能力目录登记：公共底座、Resolve、Review、Optimize、Infra/Stack、Cyber、Automation、Team。展位主页面聚焦一条事故闭环；其它模块只在能力地图显示可用、开发中或待验证，不能放成貌似可用的空入口。用户提供的《完整功能对标与蜂群架构实施规划》和 JSON 登记表是目标规划，不是当前仓库验收报告。

## 7 分钟现场路径

1. **0:00–0:30** 展示健康业务真值，让评委选择故障。
2. **0:30–1:10** 评委注入复合故障；显示受影响请求和独立探针。
3. **1:10–2:20** 打开三份来源不同的线索、成员消息与一条被反证改变的方案。
4. **2:20–3:10** 审查修复 diff、权限、旧版失败与候选版通过，批准本地测试动作。
5. **3:10–3:50** 执行后读取生效版本，观察新的业务请求和正常样例。
6. **3:50–4:20** 打开同案单 Agent 对照，报告质量、时间、总成本和失败。
7. **4:20–4:40** 展示 A 失联、B 接管、A 恢复后旧写入被拒的原始事件。
8. **4:40–7:00** 由评委点开任一证据，回答权限、EvoMap 贡献和商业落地问题。

另备 90 秒压缩讲解与带明确“历史回放”标签的无人值守画面。新运行若等待远程模型，历史证据可先供检查；不得把旧运行或录屏称为当前实时结果。

## 效果实验与完成门槛

强单 Agent 对照须获得相同模型、原始事实、工具、总预算、故障真值和冻结的验收合同；两侧状态隔离，不同时写同一个真实目标。比较整体业务恢复与误修，再比较含所有角色、验证和失败请求的耗时及总成本。禁言回答“通信是否有因果作用”，记忆开关回答“经验是否节省了具体步骤”，两者不能直接证明蜂群涌现。失败、超时、弃权、人工介入及未知用量必须保留。若单 Agent 在某类任务更好，如实限定蜂群的适用场景。

展示每项能力的最低证据：

| 能力 | 现场证据 |
| --- | --- |
| 交换线索与解决分歧 | 一条发现被另一成员引用；反证或区分性测试改变结论。 |
| 接管与安全 | 新租约接管后，旧成员写入在执行入口被拒；目标版本和权限不变。 |
| 经验复用 | 适用版本的已批准 playbook 被检索、复核后使用，记录省掉的步骤。 |
| 即插即用 | 新成员声明能力、按任务加入并受同一预算和权限门禁约束。 |
| 业务恢复 | 独立真值与正常样例通过；运行版本匹配，观察窗口足够；缺数据时保持待验证。 |
| EvoMap 集成 | 分开给出远程推理、GEP 本地资产、官方协作、Hub 经验交换各层的实际回执；未授权层显示未启用。 |

## 提交物与核对

[深圳活动官网](https://hackathon.evomap.ai/shenzhen)公开确认赛道主题和 Day 4 展示流程。[作品提交入口](https://hackathon.evomap.ai/projects/new?edition=shenzhen)先要求报名时的 11 位团队编码，公开状态无法查看后续完整字段。精确截止时间、评分细则及商业计划书是否必交，应由团队在报名后台或正式选手指南核对；不能从内部作战手册直接写成已确认的官方规则。

准备项目介绍、仓库与复跑说明、成员信息、A3 海报、90 秒标注录像，以及一份 6–8 页商业计划书 PDF。商业计划书围绕客户痛点、产品工作流、蜂群价值的可证伪实验、竞品、商业模式假设和路线；不填未验证的收入或节省率。提交材料中的性能数字和截图都应来自最终冻结源码与原始运行记录。

## 当前开发与展示的边界

公开 `main` 已有小智故障实验、真实模型请求、权限与独立验收、同案双屏和本地经验复用；`support-agent` 本地测试工作区属于尚未随本次文档上传的开发分支。历史同案样本不能证明蜂群在质量、时间或成本上超过单 Agent。官方远端协作/Hub、完整复合故障、多轮公平消融和全部公开功能对标仍各有独立验收门槛。任何历史演示图、海报或视频保留录制版本标注；源码修改后要重新构建、重启并重验现场路线。
